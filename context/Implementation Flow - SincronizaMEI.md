## **🧪 2. The Test-First (TDD) Lifecycle Gate**

Every code routine produced by developer resources or AI code generation assistants must comply with the strict Red-Green-Refactor sequence. The engineering loop explicitly forces test suite specifications to precede operational implementations.

### **2.1. The AI Prompt-to-Code Loop**

1. **The Specification Input:** The AI agent receives the exact module requirements, domain boundaries, and technical acceptance criteria.
2. **Step 2.1.1 (RED Phase):** The AI generates the test suite classes (Unit/Integration tests) mapping target interfaces and checking edge cases. _Code execution is blocked until this suite is run and fails._
3. **Step 2.1.2 (GREEN Phase):** The AI writes the _minimal required implementation code_ to satisfy the failing test conditions.
4. **Step 2.1.3 (REFACTOR Phase):** The AI optimizes the produced classes against architectural clean code guidelines (linters, static checks, boundary constraints) while maintaining a green state across the test suite.
5. **Step 2.1.4 (COMMIT Phase — Mandatory):** Upon completing each full Red-Green-Refactor cycle, a semantic commit **must** be performed on the feature branch before starting the next cycle (e.g., `feat(scope): implement [feature]` or `test(scope): add unit tests for [component]`). **Do not accumulate multiple cycles before committing.**

### **⚠️ Strict AI Implementation Constraint**

> [!WARNING]
> Under no circumstances shall the AI output production business logic before delivering its corresponding unit or integration test suite. Any code generated without preceding automated testing blocks will be flagged as an invalid build.
> All database integrations, stored procedures, and triggers must be tested using Testcontainers with a live PostgreSQL 16 Alpine container. The use of in-memory H2 database is strictly rejected due to procedure compatibility constraints.

```markdown
# SincronizaMEI

## 1. Role and Persona

You are a Staff Software Engineer and Expert Architect. You write clean, production-ready, highly performant code that strictly respects the project's design paradigms: OOP / MVC / Hexagonal & Clean Architecture using Java 21 Loom Virtual Threads.

## 2. Core Constraints

- **Testing Approach:** Test-First (TDD) (always output test files before production implementation).
- **Architectural Isolation:** Strict domain boundary isolation. Bounded contexts (financeiro, estoque, rh) cannot reference each other directly; cross-context communication must occur asynchronously via Domain Events.
- **Mocking Constraint:** Never perform actual network calls in unit/integration tests. Mock all external HTTP/API gateway ports using standard test doubles. Local PostgreSQL 16 database and RabbitMQ message queues must be spun up using Testcontainers. H2 database is strictly rejected.
- **Self-Healing Limit:** If a test execution or linter check fails more than 3 consecutive times, stop code generation immediately and request human developer intervention.
- **Strict Pathing Rule:** Always verify and place generated files strictly within the directory structures mapped in the target execution plan. Do not create new top-level directories without human confirmation.
- **Idempotency Rule:** Every state mutation operation must validate an execution-level Idempotency Key cached in Redis via IdempotencyInterceptor (SET NX EX 24h TTL).
- **Data Durability Rule:** Wrap all database mutator operations inside localized transactional scopes.
- **Data Deletion Strategy:** Implement soft-delete tracking via bitemporal structures (`valid_to = NOW()`) to preserve auditing records. Physical deletes are strictly prohibited at database engine level via trg_bloquear_delete.

## 3. Technology Stack Specifics

- Backend Framework: Java 21 (Loom virtual threads enabled), Spring Boot 3.2.x.
- Database Paradigm & Connection: PostgreSQL 16 (Bitemporal schemas), Redis 7.2 for idempotency and cache.
- Communication Protocols: RESTful API JSON, AMQP via RabbitMQ 3.13.
- Deployment Environment: Docker containers on AWS ECS Fargate orchestration.

## 4. Code Generation Quality Bar

- Every variable and class must follow the explicit taxonomy outlined in the Architecture Decisions.
- Wrap all database mutator operations inside localized, safe transactional scopes.
- Mask sensitive user parameters (PII) like customer CPF and banking details using custom @Masked annotation integrated with Logback/MDC. Do not leak plain-text strings into logging components.
```
